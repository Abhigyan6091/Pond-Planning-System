1. Executive Summary & Objective

Modern distributed systems, microservices, and compute-heavy geospatial backend services rely on observability to answer critical questions: What happened? Where was the time spent? Which exact subsystem failed and why?

The objective of this assignment is to integrate the OpenTelemetry (OTel) open standard into the existing AI-based Village Pond Planning System (Terrain Analyzer). OpenTelemetry provides vendor-neutral APIs, SDKs, and tooling to capture and export the three primary pillars of observability: 1. Distributed Tracing: Microsecond-resolution execution graphs with parent-child span hierarchies, tags, and events. 2. Application Metrics: Counters, histograms, and gauges exposing computational throughput, latency distributions, and resource utilization. 3. Correlated Logging: Log events automatically enriched with active trace_id and span_id contexts to eliminate guesswork during forensic debugging.

This report details the design, implementation, and empirical verification of OpenTelemetry within the project, complete with data captured directly from the running system, screenshot demonstrations, and an architectural analysis of system behavior.

2. System Architecture & Observability Topology

2.1 Backend Workflow & Core Pipeline

The Village Pond Planning System processes complex topographic inputs (KML/KMZ contour lines) to identify optimal water harvesting pond locations and delineate hydrologic catchment areas. Its pipeline consists of five intensive computational stages: 1. Contour Extraction & Parsing: Extracts raw KML from KMZ ZIP archives and parses multi-geometry elevation contours. 2. DEM Reconstruction: Interpolates irregular vector contours into a dense raster Digital Elevation Model (DEM) grid. 3. Pond Suitability Evaluation: Evaluates candidate topographic depressions using slope, flow accumulation, depression depth, and runoff potential. 4. Hydrologic Watershed Delineation: Executes D8 flow routing from the recommended pond outlet to compute contributing catchment area. 5. Geospatial Overlay Generation: Renders hillshade and hypsometric elevation overlays for spatial mapping.

3. Implementation Details

The OpenTelemetry subsystem is implemented cleanly and modularly in backend/telemetry.py and seamlessly integrated into the application lifecycle in backend/main.py and backend/api/contour_analysis_routes.py.

3.1 Distributed Tracing Implementation

  • Resource Definition: Standard OpenTelemetry semantic resource attributes: python resource = Resource.create({ "service.name": "village-pond-planning-system", "service.namespace": "hydrology-dem-ai", "service.version": "1.0.0", "deployment.environment": "production", "host.name": os.getenv("COMPUTERNAME", "localhost") })
  • OTLP Trace Exporter: Batched export via OTLPSpanExporter(endpoint="http://localhost:4318/v1/traces") communicating directly with Jaeger's native OpenTelemetry HTTP receiver on port 4318.
  • In-Memory Ring Buffer: An InMemorySpanRecorder collects recent finished spans (up to 250) for immediate querying via /api/telemetry/spans and live dashboard rendering.
  • FastAPI Auto-Instrumentation: FastAPIInstrumentor.instrument_app(app) instruments every HTTP route, capturing:
  • http.method (e.g. POST, GET)
  • http.route (e.g. /api/analyzeContour, /findCatchment)
  • http.status_code (e.g. 200, 400, 422, 500)
  • http.target and client parameters.
  • Domain Child Spans: Manual spans instrumenting each critical algorithmic step using tracer.start_as_current_span(...):
  • parse_contour_kml_kmz: Captures file.name, file.format, file.size_bytes, contour.count, and elevation bounds.
  • reconstruct_terrain_dem: Captures raster dem.grid_rows, dem.grid_cols, dem.total_cells, and spatial dem.pixel_size_m.
  • evaluate_pond_suitability: Captures suitability.num_candidates, suitability.top_score, and optimal coordinates.
  • delineate_catchment_watershed: Captures catchment.area_m2, catchment.area_km2, and watershed slope.
  • generate_dem_overlays: Captures visualization rendering performance.

3.2 Metrics Collection Implementation

  • Meter Provider & Reader: Configured with PrometheusMetricReader(), exposing live metrics at http://localhost:5240/metrics.
  • Custom Business & Operational Instruments: | Metric Name | Instrument Type | Unit | Description | | :--- | :--- | :--- | :--- | | village_pond_requests_total | Counter | 1 | Total API requests grouped by method, route, and HTTP status code | | village_pond_request_duration_seconds | Histogram | s | Latency distribution of HTTP endpoints across logarithmic buckets | | village_pond_analysis_duration_seconds | Histogram | s | End-to-end contour analysis and pond modeling processing latency | | village_pond_candidates_found_total | Counter | 1 | Number of viable pond candidate sites discovered per analysis | | village_pond_catchment_area_m2 | Histogram | m² | Distribution of watershed catchment areas calculated | | village_pond_active_requests | UpDownCounter | 1 | Real-time gauge of in-flight concurrent calculations | | village_pond_contours_parsed_total | Counter | 1 | Cumulative vector contour lines ingested from KML/KMZ files | | village_pond_dem_cells_processed_total | Counter | 1 | Cumulative raster elevation cells processed |

3.3 Correlated Logging Implementation

  • Context Injection: Python's standard logging library is configured via LoggingInstrumentor().instrument(set_logging_format=True).
  • Log Format: %(asctime)s [%(levelname)s] [trace_id=%(otelTraceID)s span_id=%(otelSpanID)s] %(name)s: %(message)s
  • Correlation Benefit: Whenever a log message is emitted during a request, OpenTelemetry extracts the active trace_id and span_id from the thread-local context and embeds them into the log line.
  • Dual Persistence: Logs are persisted to storage/opentelemetry.log and captured in an in-memory buffer (InMemoryLogHandler) for real-time inspection in the web dashboard.

3.4 Context Propagation & Response Headers

To facilitate end-to-end verification, custom middleware automatically injects tracing headers into all HTTP responses: - X-Trace-ID: Hex-encoded 128-bit trace ID (e.g., f585c3b465a43cc4f08a400a71ceeb83) - X-Span-ID: Hex-encoded 64-bit root span ID (e.g., 4ac0f4a5945400a4)

6. Analytical Understanding & Practical Value of OpenTelemetry

6.1 Performance Profiling & Latency Diagnostics

In geospatial hydrological modeling, processing times can vary dramatically depending on the number of contour vertices and DEM resolution. - Before OpenTelemetry: The developer only knew that an upload request took ~700 ms. If a request slowed down to 5 seconds, there was no visibility into which algorithm caused the delay. - With OpenTelemetry: The span breakdown reveals exact timing: - Vector Parsing: 42.1% of total runtime (298.9 ms). - DEM Interpolation: 18.4% of runtime (130.7 ms). - Candidate Scoring: 15.1% of runtime (107.3 ms). - Watershed Delineation: 8.0% of runtime (56.9 ms). - Overlay Generation: 4.3% of runtime (30.5 ms). This proves that parsing large KML XML trees is the primary computational bottleneck. Optimization efforts should target vector parsing (e.g. streaming SAX/iterparse) rather than the hydrology algorithms.

6.2 Root Cause Analysis & Error Pinpointing

When an invalid or corrupt file is submitted: 1. The root HTTP span records status 400 Bad Request or 422 Unprocessable Entity. 2. The failing span (parse_contour_kml_kmz) captures the exception stack trace and sets status=ERROR. 3. The correlated logs immediately display the error message alongside the trace_id. 4. An on-call engineer can take the X-Trace-ID returned to the user, enter it into Jaeger or the Telemetry Center, and immediately see the exact line of code and input data that failed, without sifting through gigabytes of unrelated logs.

6.3 Capacity Planning & SLA Monitoring via Metrics

The collected metrics provide continuous health tracking: - village_pond_requests_total allows calculation of request rates (QPS) and error percentages ($4xx/5xx$ ratio). - village_pond_request_duration_seconds allows calculating p50, p95, and p99 Service Level Objectives (SLOs). - village_pond_dem_cells_processed_total tracks backend computation volume over time, aiding server sizing and memory allocation.
